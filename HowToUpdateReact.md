# Инструкция по обновлению версии React

Обновление версии React состоит из нескольких частей:

1. Обновление исходников React
   1. Скачать свежие исходники React.
   2. Собрать JS-файлы через Rollup.
   3. Поправить в исходниках React комментарии в JSON-файлах.
2. Обновление зависимостей и публичного API.
3. Обновление смежных и зависимых библиотек:
   1. `react-testing-library`.
   2. `slate-react`.
   3. `pixi-react`.
4. Правки в `wasaby-requirejs-loader` и `builder`.
5. Исправление совместимости с Wasaby.
6. Испление платформенных контролов:
   1. Правки в юниты.
   2. Правки в компоненты.
7. Исправление прикладных контролов:
   1. Правки в юниты.
   2. Правки в компоненты.

## Обновление исходников React

### Скачать свежие исходники React

Первый шаг к обновлению - это скачивание свежих исходников React и подготовка окружения.

Исходники можно взять из официального git-репозитория.

Скачиваем исходники в:

```text
saby/react/react-source/v[xx]
```

> Главное тут надо понимать: для сборки надо переключиться на конкретный тег, который начинается с `v`.

### Собрать JS-файлы через Rollup

Есть автоматический скрипт сборки React через Rollup. Он находится в репозитории `saby/react`.

Но для его работы надо сначала подготовить окружение:

1. Проверяем версию `node.js` - проверялось на `18.17.1` управлять версиями можно через `nvm`.
2. Ставим `yarn` - обязательно, через него устанавливаются зависимости самого React.
3. Устанавливаем Java - это нужно для работы минификатора из сборки React.
4. Не забываем перезапустить консоль после установки JRE.
5. Запускаем `init` из корня:

```bash
npm run init *version*
```

Если необходимо внести изменения в исходники React, делаем это по пути:

```text
react-source/*версия*/packages
```

После подготовки окружения можно запускать скрипт.

Запускаем сборку из корневой директории:

```bash
yarn build:*версия*
```

> Скрипт успешно сработает только в случае, если структура React не будет сильно изменена.

Если скрипт не сработает, надо посмотреть ошибки и понять, в чем причина:

- неправильно настроенное окружение;
- изменение структуры React / проблемы с конфигом Rollup;
- проблемы внутри Rollup.

Скорее всего актуальна будет вторая причина. Все, что надо сделать, - это поправить конфиг. Для этого проверяем, какой именно шаг упал.

Если сборка не запустилась, то скорее всего проблема где-то в структуре React, и надо поменять пути в конфиге.

Если сборка запустилась, но упала, то надо смотреть в сторону версий Rollup и его плагинов.

Есть один нюанс при сборке исходников:

> Сейчас не собираем `react-reconciler`.
>
> Текущая версия собрана из `node_modules`.
>
> Это связано с тем, что результат из исходников и из npm при сборке отличается.
>
> А для `pixi-react` важно, какой `reconciler` собран. С собранной версией из исходников он не работает.

Поэтому в финальном файле `react-reconciler.js` надо заменить:

```js
cacheSignal: function () {
    return readContext(CacheContext).controller.signal;
}
```

на:

```js
cacheSignal: function () {
    return readContext(CacheContext).controller.signal;
},
getOwner: function () {
    return null;
}
```

После успешной сборки в `third-party` получим папку:

```text
React/third-party/v[xx]
```

В ней будут собранные JS-файлы React.

Остается проверить, что есть 2 версии:

- дебажная - например, `react.js`;
- релизная - например, `react.min.js`.

Пара дебаг/релиз должна быть у каждого файла. Если пары нет, то сборка сработала неправильно и надо проверять, какой шаг упал.

Самый простой способ - отключение шагов 5-9 в сборочном скрипте. Так можно увидеть промежуточный результат и понять, что именно пошло не так.

Также надо проверить само содержимое файлов, так как вместо дебаг-версии может собраться версия для профилирования.

Чтобы понять, что у нас полноценный дебаг, надо по исходникам React поискать комментарий:

```text
== DEV ==
```

И посмотреть код под ним. Он должен быть в финальной версии дебажных файлов. Если он есть, значит все собралось правильно.

### Поправить в исходниках React комментарии в JSON-файлах

Этот шаг нужен для того, чтобы залить исходники конкретной версии к нам на git.

Просто скачать и залить не выйдет, так как наш линтер не пропустит некоторые файлы из исходников. Для решения этой проблемы надо поправить места в исходниках. Чаще всего это комментарии в JSON-файлах.

Также для уменьшения размера исходников можно удалить все исходники плагинов, так как они нам не нужны: мы их никак не используем и никак не собираем.

## Обновление зависимостей и публичного API

### Обновление публичного API

Это самый важный этап в обновлении React.

На этом этапе нам надо понимать, какие фундаментальные изменения в публичном API появились между версиями. Для этого идем читать changelog по версиям.

Например, если обновляемся с 17 до 19, значит надо смотреть все публичные изменения в 18 и 19 версии.

После анализа изменений публичного API надо сделать массовую замену. Это очень больно, и чаще всего именно из-за этого нельзя обновить React итеративно.

В качестве альтернативы могут послужить шимы в текущую версию, но это не всегда возможно и может быть дороже, чем одна большая и сложная доброска.

### Обновление зависимостей

Между версиями могут меняться пути импорта публичных функций. Чаще всего это касается unit-тестов и конкретно `react-testing-library`.

Тут есть два пути решения:

- делать массовую замену и заливать все сразу;
- делать алиас в текущую версию, потом делать массовую замену, а потом удалять алиас.

Понять, что поменялось в импортах, можно или из changelog, или при запуске сборки/юнитов локально.

## Обновление смежных и зависимых библиотек

На самом деле этот пункт при обновлении версии может быть очень трудозатратным.

Кроме самого React у нас также используется ряд сторонних библиотек, которые работают поверх React:

1. `react-testing-library` - для юнит-тестов.
2. `slate-react` - БТР.
3. `pixi-react` - редактор схем.

### Обновление react-testing-library

Версия RTL поднимается в:

```text
saby/wasaby-cli/package.json
```

Пример зависимостей:

```json
{
    "dependencies": {
        "@testing-library/react": "14.3.1",
        "@testing-library/dom": "9.3.4",
        "@testing-library/jest-dom": "6.4.5",
        "@testing-library/user-event": "14.5.2",
        "@testing-library/react-hooks": "8.0.1"
    }
}
```

Указать новую версию в `package.json` недостаточно. Надо:

1. Проверить, что актуальная версия RTL сможет работать с доступной нам версией `Node.js`.
2. Согласовать добавление в наш npm-репозиторий пакета RTL.

> Если актуальная версия RTL не может быть запущена на доступной нам версии `node.js`, надо пробовать максимально доступную.
>
> Это не самый хороший подход, и как минимум какие-то фичи из актуальных могут не работать.
>
> Если же нужна именно актуальная версия библиотеки, то придется решать вопрос с тем, что блокирует это обновление.

### Обновление slate-react

Наш БТР написан поверх библиотеки `slate-react`.

Также с учетом наших требований к БТР есть ряд трудностей, которые не позволяют безболезненно обновить саму библиотеку:

1. Патчи в исходном коде библиотеки.
2. Логика работы оберток.

Тут единственный способ в момент обновления версии React проверить, как себя чувствует БТР, - это тесты по веткам.

Если все ок, значит версию `slate-react` можно обновлять отдельно.

Если нет, значит надо искать проблему:

- или несовместимость самой библиотеки, например при сильном изменении публичного API React;
- или проблема в наших обертках, например код ожидает какого-то поведения от рендера React, которое или поменялось, или никогда официально не гарантировалось, но на такое поведение была заточка.

### Обновление pixi-react

Еще одна библиотека, которая работает поверх React.

Ее обновление при обновлении React необходимо только если меняется публичное API React.

Из нюансов: `pixi-react` лежит на CDN, а не в `third-party` модуле.

### Правки в builder

Эти правки необходимы, если надо обновить типы React.

Вся сложность пункта в том, что надо обновить `package-lock.json`, но делать это можно только с Linux-тачки. Если попытаться сделать это из-под другой ОС, то файл будет испорчен и сборки все упадут.

## Исправление совместимости с Wasaby

Начиная с этого пункта и далее уже идет непосредственное изменение кода.

Каких-то пошаговых инструкций тут нет. Можно дать лишь общий список того, что может сломаться в совместимости при изменении версий:

- `UICore/_jsx/runtime` - в этом файле переопределяется render-функция. Если с ней что-то меняется в React, значит и тут надо будет что-то изменить.
- `UICore/_executor/_Markup/Creator/ReactTypesChecker` - здесь описываются символы, которыми помечаются `FiberNode` в React. Надо проверять, что все символы актуальные. Делать это можно поиском по исходникам React.
- `UICore/_base/Control/ClientLogic`, а также `BaseLogic` и `ServerLogic` - базовый контрол Wasaby необходимо актуализировать, если меняются хуки жизненного цикла React.
- `UI/Core/_base/Control/WasabyUpdater/*` - аналогично базовому контролу: зависят от хуков жизненного цикла.
- `UICore/_ref/*` и `UICore/_base/Refs` - изменения могут потребоваться, если меняется принцип работы ref в React.
- Система фокусов и система событий - в целом они не сильно зависят от изменений в React, но так как под капотом используются React-контролы, то при изменении API могут потребоваться какие-то доработки.

## Исправление платформенных контролов

### Правки в юниты

Правки в юниты достаточно простые, и есть несколько видов:

- Изменение импортов/API RTL - просто меняем импорты или API, делается через массовую замену.
- Не совпадают снапшоты - между версиями при рендере снапшотов могут добавляться/удаляться пустые строки в самом снапшоте. Тут выход один - обновить снапшоты.
- Тест использует удаленные в новых версиях RTL API - только переписать тест, других вариантов нет.

### Правки в контролы

Изменения в контролы необходимо вносить по месту.

Можно выделить 2 группы:

- места стыка Wasaby/React - чаще всего ломаются из-за порядка вызова хуков, если он изменился между версиями React;
- контрол написан с учетом поведения конкретной версии React, которая никогда не называлась фундаментальной, а работала лишь «потому что».

Как и с пунктом совместимости с Wasaby, четкого алгоритма исправления или списка мест, которые могут 100% сломаться при изменении версии React, нет.

Но в зоне риска:

- списки;
- окна;
- контролы, которые считают размеры контейнера до отрисовки браузером.

## Исправление прикладных контролов

### Правки в юниты

Тут все аналогично принципу исправления юнитов в платформенных контролах.

### Правки в контролы

Частных рекомендаций нет.

Из общих:

- если кто-то сам строит React-root, например видеозвонки, и если между версиями React меняется API создания корня приложения, то надо поменять места создания корня;
- контролы, написанные с учетом поведения конкретной версии React, которая никогда не называлась фундаментальной, а работала лишь «потому что».
